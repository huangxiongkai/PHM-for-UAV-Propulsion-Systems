# **项目基本信息：**

无人机动力系统瞬态预测与动态降级系统

**目标**： 掌握 ADC DMA 高频抗干扰采集、离散数据微分预测算法与 RT-Thread 事件集驱动的闭环控制。

模拟场景： 将电位器模拟为“动力电池电压”（模拟带纹波的瞬间掉电），热敏电阻模拟为“电机/电调温度”（模拟热惯性），蜂鸣器作为“预警器”，一路 PWM 输出模拟“飞控油门信号”作为“降级执行器”。

**具体任务：**
硬件层： 开启 ADC 的 DMA 连续扫描模式，高频采集电位器与热敏电阻数据；配置两路定时器 PWM，分别用于驱动蜂鸣器和输出模拟油门限幅信号。

**RTT 融入（线程）：**


Acquire\_Thread：高频（如 100Hz）从 DMA 缓冲区提取原始数据，执行中值/滑动平均滤波洗去噪声，计算当前真实的电压与温度绝对值。

Predict\_Thread：接收绝对值数据，计算电压变化率与温升速率，打包绝对值与变化率指标发送。

Supervisor\_Thread：运行滞回状态机，综合绝对值与微分变化率判定系统健康度（安全/预警/危险），通过事件集发布状态。

Actuator\_Thread：阻塞等待特定事件组合。接收到预警事件，蜂鸣器慢响，输出 PWM 将油门限幅至 80%；接收到危险事件（如急剧升温且掉电），蜂鸣器急促响，输出 PWM 强制将油门限幅至 50% 迫降。

Display\_Thread：显示实时电压/温度、当前健康状态及动力限幅比例。

特别注意： 学习如何利用 RTT 的 事件集 实现多条件组合逻辑判定（如 dV/dt 骤降 AND 绝对电压偏低）；掌握滞回比较器的设计，防止阈值边界抖动引发“报警风暴”；深刻理解“变化率预测”比“绝对值报警”在防范瞬态坠机中的工程价值。



**效果**： 快速拧动电位器模拟电池瞬间大电流放电，即使电压绝对值未跌至危险线，dV/dt 预警也会立刻触发蜂鸣器并自动降低油门上限；对热敏电阻哈气模拟急剧升温，dT/dt 预警提前介入限幅。实现从“被动报警”到“主动干预保全”的闭环。

# ������ 项目开发书：无人机动力系统瞬态故障预测与动态降级系统

### 一、 项目背景（基于真实坠机因素）
无人机坠毁极少由单一瞬间故障导致，往往是动力系统处于临界状态（电池临界内阻、电机临界温度）时，叠加一个瞬间机动动作，引发雪崩效应（电压骤降->飞控重启->炸机）。
传统的电压/温度报警系统存在致命缺陷：
1. **报警滞后**：当检测到低压时，电池往往已处于极度亏电状态，无力支撑返航。
2. **缺乏预测**：温度是惯性系统，等检测到高温报警时，电机磁钢可能已发生不可逆退磁。
3. **只报不防**：蜂鸣器报警对飞手毫无意义，飞手在空中无法修数据，真正需要的是系统自动限制动力输出，强行维稳。

### 二、 核心功能与技术突破（简历核心亮点）
本项目旨在构建一套独立于飞控的安全副驾驶系统，实现从“事后报警”到“事前干预”的跨越。

1. **瞬态压降捕获（$dV/dt$ 监控）**：
   *   不仅监控当前电压，更通过连续高频采样计算**电压变化率**。当电压瞬间跌落斜率超过阈值时，即使绝对电压未降至危险线，也判定为电池内阻过大或瞬时过载，提前触发保护。
2. **热惯性预测（$dT/dt$ 监控）**：
   *   利用热敏电阻高频采样，计算**温升速率**。如果电机在短时间内急剧升温，即使当前温度还在安全范围内，系统也预测其即将过热，提前介入。
3. **动态功率降级（闭环干预）**：
   *   摒弃单纯的蜂鸣器报警。当系统预判危险时，输出一路PWM信号（模拟油门限幅信号），动态削减飞控的最大油门输出，强制飞机进入“缓释模式”，避免坠机。
4. **强抗干扰底层采样**：
   *   采用ADC DMA+过采样+滑动窗口滤波，剥离电调产生的高频纹波，确保底层数据的真实性。

### ������ APP层 (业务与控制)
负责核心业务逻辑、状态判定与闭环干预。

- **`app_acquire.c/h` —— 数据洗涤线程**
  - **核心职责**：从 DMA 缓冲区提取原始数据，执行数字滤波洗去噪声，计算当前真实的电压与温度绝对值。
  - **关键技术**：过采样算法、一阶滞后滤波、中值滤波

- **`app_predict.c/h` —— 趋势预测线程**
  - **核心职责**：接收洗涤后的绝对值数据，计算电压/温度的微分（变化率 $dV/dt$ 与 $dT/dt$），输出预测指标。
  - **关键技术**：离散差分算法、动态窗口斜率计算

- **`app_supervisor.c/h` —— 安全监督状态机**
  - **核心职责**：综合绝对值与微分值，运行多级滞回状态机，判定系统健康度，并通过事件集发布状态。
  - **关键技术**：滞回比较器、多条件逻辑判定、`rt_event_send`

- **`app_actuator.c/h` —— 执行与降级线程**
  - **核心职责**：阻塞等待特定事件组合，执行分级动作（预警蜂鸣 / 限制油门 PWM 输出）。
  - **关键技术**：`rt_event_recv`、PWM 输出限幅逻辑

- **`app_display.c/h` —— UI线程**
  - **核心职责**：接收状态消息队列，显示实时数据及系统干预状态（如：当前动力输出百分比）。
  - **关键技术**：`rt_mq_recv`

### 🔄 阶段一：原教旨循环流 —— DMA Circular + HT/TC 直读

这是初学者和教科书最常用的设计，依赖 DMA 开启 Circular 模式的全自动化特性。

*   **核心思路**：DMA 开启 Circular 模式死命跑，触发半传输中断（HT）时线程去读前半段，触发全传输中断（TC）时线程去读后半段，减少 CPU 干预。
*   **演变动因**：为解决 Normal 模式下每传完一轮需要 CPU 手动重启 DMA 的问题，追求全自动化闭环。
*   ❌ **致命缺点 —— 数据撕裂**
    *   在裸机（无 RTOS）环境中，中断触发后直接在 while(1) 内处理，此方案完全可行。
    *   **但在 RT-Thread 环境下是灾难**：中断释放信号量后，Acquire_Thread 并不能立即执行，它需要等待 OS 调度抢占。如果期间有高优先级任务（SBUS 解析、OLED 刷新）占用了 CPU，等到你的线程终于读到 DMA 缓冲区时，DMA 可能已经写入了 20 个新数据。你算出来的平均值，是一半旧数据一半新数据，电压值会莫名其妙地跳变。

### 🛑 阶段二：矫枉过正的急停流 —— DMA Normal + 中停/重启

发现数据撕裂后，直觉反应是：**只要 DMA 停下来，数据就是安全的！**

*   **核心思路**：DMA 设为 Normal 模式，传满后触发 TC 中断。在线程中先把 DMA 甚至 TIM3 停掉，等线程慢慢算完平均值，再手动重新开启新一轮采集。
*   **演变动因**：为了绝对杜绝数据撕裂，采用一刀切的物理隔离法。部分早期开源项目在极度受限的 RAM 下也偶尔采用此思路。
*   ❌ **两大致命暴雷**：
    1.  **HAL 库状态机死锁（工程灾难）**：STM32 的 HAL 库状态机极其脆弱。在高频中断中连续调用 HAL_ADC_Stop_DMA() + HAL_ADC_Start_DMA()，极易导致内部状态机卡死在 BUSY 状态，DMA 从此再也运行不起来。这就是你之前串口**按复位才更新一次**的根本原因。
    2.  **时基断点（数学灾难）**：重启 DMA 需要时间（清寄存器、重配指针），在此死区内 TIM3 发出的触发脉冲会被 ADC 忽略（Overrun）。相邻两个 5ms 窗口之间存在一道时间裂缝，对于《技术报告》要求的 dV/dt 离散微分计算，时基不连续会导致微分结果瞬间发散，产生高频毛刺。

---
### 🏆 阶段三：工业级影子流 —— DMA Circular + HT/TC + 影子缓冲（最终定案）

引入飞控领域的**空间换时间**思想，这也是 PX4、Betaflight 等现代高端飞控在 F4/H7 上的标准范式。

*   **核心思路**：
    1.  TIM3 和 DMA Circular **永不停歇**，保证了时基绝对连续（无死区，数学严密）。
    2.  在 HT/TC 中断触发的那一瞬间，用极速的 memcpy 把刚写完的那半段数据，拷贝到一个独立的**影子数组**中。
    3.  业务线程只从影子数组读数据，DMA 继续自由地写物理缓冲区，**物理隔离、零等待、零死锁**。
*   ✅ **为什么能完美解决所有问题？**
    *   **防撕裂**：HT 中断触发时，DMA 硬件自动开始写后半段，前半段处于硬件级安全期。用十几微秒把前半段拷走，物理上绝对隔离。
    *   **防死锁**：再也不碰 HAL_ADC_Stop_DMA，外设状态机永远处于健康运转状态。
    *   **保时基**：TIM3 的触发脉冲一个没漏，64 个点在 5ms 内绝对等距，dV/dt 算法的数学前提完美成立。

### 📌 最终定案：DMA Circular + 双中断影子拷贝 + TIM3 定频触发

*   **零撕裂 / 零死锁**：DMA 配置为 Circular 永不重启。HT/TC 中断触发时，利用 memcpy 将已就绪的半区数据瞬间冻结至独立的 adc_shadow_buf。CPU 读影子区，DMA 写物理区，物理隔离彻底根除覆盖问题。
*   **零时基抖动**：采样时钟由硬件定时器锁定，时间窗口积分真实反映物理能量，完美支撑离散微分算法。
*   **RTOS 调度优化**：中断仅做极速拷贝与信号量释放（rt_sem_release），耗时滤波与解算完全下沉至 Acquire_Thread 阻塞处理。按 shadow_ready_half 标志位读取对应半区，状态机极简，无额外调度负担。

【困难三】：在进行oled的移植时出现了以下问题：
1. 通信机制的严重隐患（HAL vs RT-Thread）
  你在 oled.c 中直接调用了 HAL_I2C_Master_Transmit(&hi2c1, ...)。
   * 问题：HAL 库是阻塞且非线程安全的。如果在 app_display.c 的线程执行期间，另一个线程也尝试操作同一条 I2C总线，或者你在中断中调用了该驱动，将导致 I2C 总线锁死 或 数据错乱。
【1.修改方向】：正如之前提到的，你应该将 OLED_Send 接口替换为 RT-Thread 的 rt_i2c_transfer。这不仅能利用 RT-Thread的设备驱动管理，还能自动处理线程互斥。

2.初始化流程冲突（main vs app_display.c）
   * 现状：你在 applications/main.c 的 main() 中调用了 OLED_Init()，同时又在 modules/app/app_display.c 中创建了Show_thread2 线程，里面直接开始绘图。
   * 问题：如果系统启动较快，main() 中的初始化可能还没彻底完成，显示线程就已经开始发送数据了。
【2.修改方向】：建议将 OLED_Init() 从 main() 中移出，直接放入 app_display.c 的线程入口中，并在线程启动时使用rt_thread_mdelay(100) 确保上电稳定。这样能确保驱动的独立性，符合 RT-Thread 的模块化开发思路。





【困难四】：电池内阻导致的瞬态压降公式为 $V_{drop} = I \times R_{internal}$。由于无人机打杆是瞬间的，电流 $I$ 会呈现阶跃上升，导致电压 $V$ 呈现阶跃下降。它不是一个缓慢的斜坡，因此 $\frac{dV}{dt}$ 在实际抓取时可能只是一个瞬间的脉冲（Impulse），滑动窗口可能会把这个脉冲平滑掉，导致漏报。
【修改方向】：对温度监控保留 $\frac{dT}{dt}$（因为热量积累是典型的积分延迟过程，斜率预测极度有效）；对电压监控，建议改为“动态基准差分法”，即比较“过去 1 秒的稳态平均电压”与“当前 5ms 的瞬态电压”的差值 $\Delta V$

【细节补充】面试官可能会问的坑：

为什么不用 DMA Circular？ 答：Circular 模式下 DMA 会持续覆盖缓冲区，RTOS 线程调度期间会产生新旧数据撕裂，导致均值计算波动。改用 Normal 模式在传输完成后停机重启，实现了天然的“软 Ping-Pong 缓冲”，保证数据原子性。
为什么采样率定 10kHz 而不是更高？ 答：硬件 RC 已削平高频尖峰，10kHz 满足奈奎斯特定理且留有裕量。过高的采样率会线性增加 RAM 占用和循环计算开销，10kHz (50点/5ms) 是 F103 在实时性和算力之间的最优折中。
